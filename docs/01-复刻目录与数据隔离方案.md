## MySQL 隔离方案

已使用独立数据库 `news_app_day06_00`；通过实际查询 `SELECT DATABASE()` 核对。原件 `database.sql` 中仍保留旧库名，但运行初始化只使用派生 SQL。

实际实施范围：

1. 保留 `sql/database.sql` 原件。
2. 派生 `sql/database.day06-00.sql`，将原件第 3 行的建库名称、第 5 行的 `USE` 名称改成 `news_app_day06_00`。审查修复后另加令牌与历史的唯一约束；原始 `database.sql` 保留不动。
3. `config/db_conf.py` 从本机环境配置读取连接 URL，目标数据库明确为 `news_app_day06_00`，默认值也不能回落到旧库 `news_app`。
4. 导入前只读检查目标库是否存在、是否已有数据。目标库为空才执行首次初始化；若已有内容，先核对来源与记录数，不能直接重复执行全部初始化 INSERT。

原件包含 `USE news_app`，所以仅在导入命令中指定新库名，不能保证导入到新库。必须同步修改派生 SQL 内部的选库语句。

初始化预期为 8 张表、8 个分类、403 条新闻、1 个素材测试用户。8 张表为 `user`、`user_token`、`news_category`、`news`、`related_news`、`favorite`、`history`、`ai_chat`。

复刻阶段以 SQL 建表为准，不改用各模块 `Base.metadata.create_all()` 取代它。当前模型分属多个 `Base`，而且只覆盖六张表；SQL 还定义了外键级联、无符号整数、时间默认值和初始化新闻。

## Redis 隔离方案

保留现有 Redis 实例与默认逻辑库 0，给所有本项目缓存键统一增加 `day06_00:` 前缀。这比随意选择一个尚未核实用途的逻辑库更明确，也能保持课程原有连接方式。

已新增后端变量 `CACHE_KEY_PREFIX=day06_00:`，在 `cache/news_cache.py` 集中生成键。举例：

- 分类：`day06_00:news:categories:{skip}:{limit}`。
- 列表：`day06_00:news_list:{category_id}:{page}:{size}`。
- 详情：`day06_00:news:detail:{news_id}`。
- 相关新闻：`day06_00:news:related:{news_id}:{category_id}:{limit}`。

分类缓存要包含 `skip`、`limit`，相关新闻缓存要包含 `limit`，避免不同查询条件共用一份结果。

只允许删除本项目前缀下的键，不能执行 `FLUSHDB` 或 `FLUSHALL`。旧项目的数据库与缓存不作为本项目的测试数据来源。

## 服务端口与浏览器数据隔离

当前后端地址为 `http://127.0.0.1:19000`，前端地址为 `http://127.0.0.1:5176`。这两个服务均已启动并完成联调。

已在 `frontend/vite.config.js` 设置前端端口 5176 和 `strictPort: true`，被占用时明确报错，不自动换端口。后端启动前也检查 19000 是否空闲。

`frontend/src/config/api.js` 读取 `VITE_API_BASE_URL`，其本项目默认值为 `http://127.0.0.1:19000`。后端 CORS 允许实际使用的本项目开发源。

浏览器按协议、主机和端口区分本地存储。固定使用 `127.0.0.1:5176`，可将这份前端的登录信息、收藏和历史本地状态与旧前端常用的 5173 源分开。不要交替使用 `localhost` 和 `127.0.0.1` 后误以为登录状态应当相同。
