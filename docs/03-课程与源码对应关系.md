# AI 掘金头条课程与源码对应关系

本说明按第三章至第六章，把课件主题、现有源码入口和真实请求流程串起来。文件名和函数已从 `day06-00` 当前文件核对；“代码存在”与“运行验证通过”分别记录。

PDF 页码按文件实际页面从 1 开始计数。课件提供示例与流程，不能据此证明下载源码与老师最终版本逐字一致。

## 第三章 新闻模块

来源：[第三章 新闻模块课件](../../../笔记/第三章_AI掘金头条-新闻模块.pdf)，重点为第 3、5、18、25、28～29 页。带 `(1)` 后缀的第三章 PDF 与本文件字节摘要相同，使用其中一份即可。

### 工程结构与路由挂载

课件第 5 页的路由、模型、数据库操作、验证模型、配置与工具，分别对应 `routers/`、`models/`、`crud/`、`schemas/`、`config/`、`utils/`。

入口是 [main.py](../main.py)，它创建 FastAPI 应用、注册异常处理器、配置 CORS，并挂载四个 Router。前端入口是 [frontend/src/main.js](../frontend/src/main.js)，负责 Vue、路由、Pinia、Vant 和国际化初始化。

### 获取分类

前端 [Home.vue](../frontend/src/views/Home.vue) 调用 [news Store](../frontend/src/store/modules/news.js) 的 `getCategories()`，请求 `GET /api/news/categories`。

后端 [routers/news.py](../routers/news.py) 的 `get_categories()` 注入 `get_db`，调用 [crud/news_cache.py](../crud/news_cache.py) 的同名函数。当前流程是查分类缓存、未命中时查询 `Category`、序列化、写缓存、返回数据。

分类表是 `news_category`，对应 [models/news.py](../models/news.py) 的 `Category`。课件第 18 页的模块化路由和分类接口与此相符。

### 获取新闻列表

`getNewsList()` 请求 `GET /api/news/list`，前端传 `categoryId`、`page`、`pageSize`；路由映射为 Python 参数 `category_id`、`page`、`page_size`。

路由计算 `offset = (page - 1) * page_size`，从 `crud/news_cache.get_news_list()` 获取当前分类的新闻，再调用 `crud/news.get_news_count()` 查询总数。`hasMore` 根据偏移量、当前条数和总数计算。

列表表为 `news`，模型为 `News`。第 25 页的列表结构包括 `list`、`total`、`hasMore`；当前后端已有这些字段，前端已使用 `hasMore` 判断加载是否结束。

发布时间字段已修正：新闻列表、收藏和历史对外统一使用 `publishTime`；Python 与缓存内部继续使用 `publish_time`。

### 获取新闻详情与浏览量

[NewsDetail.vue](../frontend/src/views/NewsDetail.vue) 调用 `getNewsDetail(id)`，请求 `GET /api/news/detail?id=新闻ID`。

后端链路为：

1. `routers.news.get_news_detail()`。
2. `crud.news_cache.get_news_detail()`：缓存或数据库读取新闻。
3. `crud.news.increase_news_views()`：数据库执行浏览量加 1。
4. `crud.news_cache.get_related_news()`：查询同分类其他新闻。
5. 路由返回正文、`publishTime`、浏览量和 `relatedNews`。

这对应第 28～29 页的详情、浏览量与同类推荐流程。源码保留无缓存版 `crud/news.py` 与带缓存版 `crud/news_cache.py`，最终路由的读取主要使用后者。

SQL 中的 `related_news` 关联表没有被当前链路使用。同类推荐查询已有实现，所以不因多出这张表就补写推荐系统。

## 第四章 用户模块

来源：[第四章 用户模块课件](../../../笔记/第四章_AI掘金头条-用户模块.pdf)，重点为第 4、8、11、13、14、16、19、21 页。

### 注册与登录

[Register.vue](../frontend/src/views/Register.vue)、[Login.vue](../frontend/src/views/Login.vue) 调用 [user Store](../frontend/src/store/user.js) 的 `register()`、`login()`，分别请求：

- `POST /api/user/register`。
- `POST /api/user/login`。

路由在 [routers/users.py](../routers/users.py)，数据库操作在 [crud/users.py](../crud/users.py)。注册先按用户名查重，再调用 `create_user()`；密码通过 [utils/security.py](../utils/security.py) 的 `get_hash_password()` 进行 bcrypt 处理。

登录调用 `authenticate_user()`，其中 `verify_password()` 检查密码。注册或登录成功后调用 `create_token()`，生成 UUID 字符串并存入 `user_token`，当前过期时间为 7 天。这是数据库存储的随机令牌，不是 JWT。

`User`、`UserToken` 在 [models/users.py](../models/users.py)，返回数据模型在 [schemas/users.py](../schemas/users.py)。成功响应包含 `token` 和 `userInfo`。

### 获取与更新用户信息

[Profile.vue](../frontend/src/views/Profile.vue) 调用 Store 获取用户或修改简介，分别请求 `GET /api/user/info`、`PUT /api/user/update`。

需要登录的路由通过 `Depends(get_current_user)` 复用 [utils/auth.py](../utils/auth.py) 的身份验证。它读取 `Authorization`，支持当前前端直接传令牌的写法，再调用 `get_user_by_token()` 核对有效期并查询用户。

信息更新使用 `UserUpdateRequest` 与 `crud.users.update_user()`；当前界面主要提供简介修改，后端同时接收昵称、头像、性别和手机号等字段。不能把后端接收字段全部写成已具备完整界面。

### 修改密码

Profile 页面调用 Store 的 `updatePassword()`，请求 `PUT /api/user/password`，提交 `oldPassword` 和 `newPassword`。

路由使用 `UserChangePasswordRequest`，CRUD 的 `change_password()` 校验旧密码、计算新哈希并提交。旧密码错误已修正为 400；改密后新密码可登录、旧密码不能登录。课程原有令牌生命周期保留，没有新增撤销旧令牌扩展。

### 通用响应与异常处理

第 11 页对应 [utils/response.py](../utils/response.py) 的 `success_response()`：将 `code`、`message`、`data` 组成结果，再通过 `jsonable_encoder` 转换可序列化数据。

第 13 页对应 [utils/exception.py](../utils/exception.py) 的四类处理函数，以及 [utils/exception_handlers.py](../utils/exception_handlers.py) 的注册顺序；`main.py` 调用 `register_exception_handlers(app)`。

请求验证错误还可能由 FastAPI 默认处理，不能将当前状态表述为所有错误都已统一成自定义格式。

## 第五章 收藏与浏览历史

来源：[第五章 收藏和浏览历史课件](../../../笔记/第五章_AI掘金头条-收藏和浏览历史.pdf)。收藏接口对应第 4、6、8、10、12 页；浏览历史对应第 23、25、27、29 页。

### 收藏链路

新闻详情页面调用 [favorite Store](../frontend/src/store/modules/favorite.js) 的状态检查和收藏切换方法；[Favorite.vue](../frontend/src/views/Favorite.vue) 加载列表并提供取消、清空操作。

五个接口为：

- `GET /api/favorite/check?newsId=新闻ID`。
- `POST /api/favorite/add`，请求体包含 `newsId`。
- `DELETE /api/favorite/remove?newsId=新闻ID`。
- `GET /api/favorite/list?page=页码&pageSize=数量`。
- `DELETE /api/favorite/clear`。

路由在 [routers/favorite.py](../routers/favorite.py)，操作在 [crud/favorite.py](../crud/favorite.py)，模型在 [models/favorite.py](../models/favorite.py)，响应在 [schemas/favorite.py](../schemas/favorite.py)。

列表查询联结 `News` 和 `Favorite`，附带 `favoriteTime`、`favoriteId`；一条列表记录的 `id` 仍是新闻 ID。收藏唯一约束由数据库限制同一用户与同一新闻只能出现一次。

### 浏览历史链路

登录用户打开新闻详情时，页面调用 [history Store](../frontend/src/store/modules/history.js) 的 `addHistoryApi()`，请求 `POST /api/history/add`，提交 `newsId`。

后端 [crud/history.py](../crud/history.py) 的 `add_history()` 查询同一用户、同一新闻是否已有历史：已有时更新 `view_time`，没有时新增记录。这与收藏“添加一次”的行为不同。

[History.vue](../frontend/src/views/History.vue) 请求 `GET /api/history/list`。后端联结新闻和历史表，返回新闻字段、`viewTime` 与 `historyId`，对应 [schemas/history.py](../schemas/history.py)。

删除接口为 `DELETE /api/history/delete/{history_id}`，清空接口为 `DELETE /api/history/clear`。当前 CRUD 和前端传参已统一使用 `historyId`；后端按用户 ID 与 `History.id` 删除，已通过 ID 不相等和其他用户越权测试。

必须区分：点击详情用新闻 `id`，删除服务端浏览记录用 `historyId`；所有服务端删除均带用户归属条件。游客本地记录是另一条前端分支，不代表已有服务端历史记录。

## 第六章 Redis 缓存与模型调用

来源：[第六章 缓存和调用模型课件](../../../笔记/第六章_AI掘金头条-缓存和调用模型.pdf)，重点为第 10、12、14～16、18～19 页。

### Redis 客户端与序列化

[config/cache_conf.py](../config/cache_conf.py) 使用 `redis.asyncio.Redis` 创建客户端：

- `get_cache()` 读取字符串。
- `get_json_cache()` 读取并反序列化 JSON。
- `set_cache()` 将字典或列表序列化，使用 `setex` 写入并设置过期时间。
- `delete_cache()` 删除指定键，实际删除返回 `True`，键不存在或操作失败返回 `False`。
- `exists_cache()` 判断指定键是否存在，返回布尔值；操作失败返回 `False`。

以上覆盖课件第 12 页列出的 `setex`、`get`、`delete`、`exists`。调用时传入完整缓存键，业务层负责添加本项目的 `day06_00:` 前缀。

客户端操作捕获异常，缓存失败时返回空值或失败状态，让上层继续查数据库。当前未用 `aioredis` 包实现这条流程。

### 旁路缓存

[cache/news_cache.py](../cache/news_cache.py) 负责业务键及缓存读写；[crud/news_cache.py](../crud/news_cache.py) 负责缓存与数据库之间的选择。

读取顺序为：查询缓存；命中则返回或重建新闻对象；未命中则查数据库；将结果转换为 JSON 可存数据；写缓存；响应前端。对应第 14～16 页。

当前有分类、新闻列表、新闻详情与相关新闻缓存，没有后端设计说明中描述的用户历史缓存和完整更新清除机制。

课件第 15 页建议分类 7200 秒、列表 600 秒、详情 1800 秒；当前代码已统一为分类 7200 秒、列表 600 秒、详情 1800 秒，与课件建议一致；素材原代码此前为列表 1800 秒、详情 300 秒。

缓存中的对象经过序列化和重建，不等同于原来绑定数据库会话的 ORM 对象；这也是详情缓存命中后浏览量不能只依赖内存对象自动更新的原因。

### 前端千问对话

[AIChat.vue](../frontend/src/views/AIChat.vue) 从 [api.js](../frontend/src/config/api.js) 读取模型端点、Key 和模型名，用 `fetch` 提交消息历史，开启 `stream: true`，逐段读取响应并追加文本。

模型输出使用 `marked` 解析 Markdown，再由 DOMPurify 清理 HTML。这是已有前端调用与展示代码，本轮已经在浏览器验证 DeepSeek 流式回复；千问入口保留，但本轮没有验证千问服务。

第 18～19 页明确要求在前端配置模型，因此当前没有后端 `/api/ai` Router，也没有对 SQL `ai_chat` 表的写入。聊天消息目前在组件内存中管理。

## 建议学习与执行顺序

1. 阅读 `main.py` 与目录职责，理解前端独立启动和后端 Router 挂载。
2. 阅读新闻的分类、列表、详情三条链路；先理解未缓存版 CRUD，再对照带缓存版。
3. 阅读用户注册、登录、Token 认证及通用响应。
4. 阅读收藏和历史的联表查询，区分新闻 ID、收藏 ID、历史 ID。
5. 阅读 Redis 读写与对象转换，再理解缓存命中路径中的浏览量问题。
6. 阅读前端千问请求和流式输出，最后进行真实模型验证。

代码执行顺序仍以 [最小调整与验收清单](02-最小调整与验收清单.md) 为准：环境和数据隔离先于业务联调。
